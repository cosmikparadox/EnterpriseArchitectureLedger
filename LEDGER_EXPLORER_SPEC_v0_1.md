## 0. READ THIS FIRST

You are building a teaching tool, not a product. It exists so that a
practising architect and an executive who has never heard of a dependency
graph can both look at the same screen and understand five ideas:

```
1  A platform is a shared node. Use cases plug into it.
2  Part of every shared node's cost is a rule, not a meter reading.
3  Risk travels along edges. Fan-in is blast radius.
4  Platforms grow by accretion. Exit cost accrues silently.
5  Diversifying vendors relocates concentration, it does not
   remove it.
```

Every number in this tool is SYNTHETIC and must be labelled as such on
screen at all times. Nothing here is drawn from the canonical Architecture
Ledger documents and nothing here changes any formula in them. If a formula
below conflicts with your memory of the canon, the canon wins and you flag
the conflict in the README rather than resolving it silently.

**Hard rules**

```
+----+-----------------------------------------------------------+
| A  | Vendor-neutral. Named systems appear as landscape          |
|    | furniture only. No evaluative statement about any vendor. |
|    | No vendor logos. No vendor colours.                       |
+----+-----------------------------------------------------------+
| B  | Do not name Snowflake anywhere. Use "cloud data platform" |
|    | or an invented name.                                      |
+----+-----------------------------------------------------------+
| C  | The tool computes only the three ledger axes: metered     |
```

Two readers, one screen.

```
Executive      Wants to see the picture move, click a thing, get a

Practitioner   Wants to open the panel, see the numbers behind the
```

## 3. THE SYNTHETIC ESTATE

A mid-size UK general insurer. Invented name: **Harbourline Insurance**.
Roughly 4,000 staff, personal and commercial lines, direct and broker
channels. Realistic enough that an architect nods; invented enough that
nobody sues.

### 3.1 Node types

```
+-------------+---------------------------------------------------+
| platform    | A shared system. Has a fixed cost pool and a       |
|             | metered driver. Examples below.                    |
| integration | The layer that stitches platforms: iPaaS, API      |
|             | gateway, event bus, identity. ALSO a platform, but |
|             | rendered distinctly because section 7 depends on   |
|             | showing it as a place concentration relocates to.  |
| use_case    | The unit of account. One use case in one declared  |
|             | business subdomain. Consumes platforms via edges.  |
+-------------+---------------------------------------------------+
```

### 3.2 Platforms (about 14)

Use recognisable categories with well-known third-party names as
landscape furniture. Attach no adjectives.

```
CRM                        Salesforce
ITSM                       ServiceNow
ERP / GL                   SAP S/4HANA
HCM                        Workday
Policy admin (P&C)         Guidewire PolicyCenter
Claims                     Guidewire ClaimCenter
Billing                    Guidewire BillingCenter
Cloud data platform        invented: "Meridian Data Cloud"
BI                         Power BI
Marketing automation       Salesforce Marketing Cloud
Document management        OpenText
Payments                   Adyen
iPaaS (integration)        invented: "Conduit iPaaS"
API gateway (integration)  Apigee
Identity (integration)     Okta
Event bus (integration)    Confluent Kafka
```

Each platform record:

```
id, name, category, type (platform | integration)
fixed_pool_gbp_month      the part that does not move with use
driver_name               e.g. "API calls", "credits", "seats",
                          "documents", "transactions"
driver_unit_cost_gbp      metered price per driver unit
capacity_note             one line, plain English
failure_lef               loss event frequency per year, base rate
failure_loss_lognormal    {mu, sigma} for direct loss in GBP
exit_execution_gbp        cost to migrate off, today
exit_option_gbp           the option component of switching cost
                          (see 5.4). Grows with tenure and fan-in.
adopted_month             when it landed on the estate (for 6)
```

### 3.3 Subdomains (declared boundaries)

Six named business subdomains. These are DECLARED. The generator does
not derive them from the graph. That is the point.

```
Sales & Distribution      quote, bind, broker portal, renewal
Claims                    FNOL, triage, settlement, fraud referral
Finance                   GL close, reinsurance settlement, IFRS 17
Customer Service          contact centre, self-service, complaints
People                    onboarding, payroll, learning
Data & Analytics          pricing model refresh, regulatory reports
```

### 3.4 Use cases (about 30)

Five per subdomain. Each use case record:

```
id, name, subdomain
volume_per_month          business volume, e.g. quotes, claims,
                          payslips. This is the coefficient base.
edges: [ { platform_id, driver_units_per_volume_unit,
           conditional_failure_prob } ]
```

Example, so the shape is unambiguous:

```
{
  "id": "uc_quote_and_bind",
  "name": "Quote and bind (direct)",
  "subdomain": "Sales & Distribution",
  "volume_per_month": 48000,
  "edges": [
    { "platform_id": "salesforce",   "driver_units_per_volume_unit": 6,
      "conditional_failure_prob": 0.9 },
    { "platform_id": "policycenter", "driver_units_per_volume_unit": 1,
      "conditional_failure_prob": 1.0 },
    { "platform_id": "apigee",       "driver_units_per_volume_unit": 14,
      "conditional_failure_prob": 0.7 },
    { "platform_id": "okta",         "driver_units_per_volume_unit": 2,
      "conditional_failure_prob": 1.0 },
    { "platform_id": "meridian",     "driver_units_per_volume_unit": 0.4,
      "conditional_failure_prob": 0.3 }
  ]
}
```

`conditional_failure_prob` is the probability the use case is
unavailable given that the platform is unavailable. It is an edge
property. This is how risk propagates.

### 3.5 Realism checks the generator must pass

```
Every use case touches at least one integration node.
Identity has fan-in from nearly everything.
The cloud data platform has HIGH fan-in from Data & Analytics
  and MEDIUM fan-in from every other subdomain (feeds).
Claims subdomain rides ClaimCenter, ServiceNow, Salesforce,
  OpenText, Adyen, Kafka.
At least four use cases cross three or more subdomain
  boundaries in their dependency chain (via shared platforms).
No use case is an island.
```

## 4. VIEWS

Six views, selected from a persistent left rail (desktop) or bottom
tab strip (mobile). Each view is a lens on the same graph. The camera
position persists across views so the user does not lose their place.

```
1  Explore        the graph, boundaries, click anything
2  Fixed pool     meter versus rule, per node, per use case
3  Risk           propagation, blast radius, exceedance curve
4  Footprint      time scrubber, accretion, exit cost accruing
5  Two shapes     concentrate versus best of breed, side by side
6  Boundaries     redraw the declared lines, watch what moves
```

### 4.1 View 1: Explore

Force-directed 3D graph. Platforms as larger spheres, integration
nodes as octahedra (distinct silhouette), use cases as small spheres.
Edge thickness proportional to metered spend flowing along it.

Subdomain boundaries rendered as translucent convex hulls around each
subdomain's use cases. Hulls can be toggled. Because platforms are
shared, hulls will overlap around shared nodes. Do not hide this.
The overlap IS the lesson.

Interactions:

```
orbit / pan / zoom        standard, touch-enabled
tap node                  opens the detail panel (section 5)
tap edge                  shows driver, units per volume, monthly
                          spend on that edge, conditional failure
                          probability
hover (desktop)           highlights the node's neighbourhood
search                    type a name, camera flies to it
toggle hulls              on / off
toggle labels             all / selected / none
isolate subdomain         dims everything outside one subdomain,
                          keeps shared platforms lit
```

### 4.2 View 2: Fixed pool

Purpose: make the meter-versus-rule split visible.

Each platform node becomes a ring (donut) drawn around the sphere in
screen space. The ring is split: metered share (solid) and rule share
(hatched). The rule share is the fixed pool allocated by the current
rule.

Panel controls:

```
Allocation rule       equal split (default) | by volume | by
                      headcount (subdomain size). Equal split is
                      the default because the canon says so.
Fan-in slider         adds or removes synthetic use cases riding
                      a selected platform, live. Watch the rule
                      share on every existing use case move.
Show C1 annotation    on / off. Per node, prints the proportion
                      of reported cost resting on the rule.
```

What the user must be able to see within ten seconds: pick the identity
node, drag the fan-in slider up, and watch the rule share on a single
use case's figure change even though that use case did nothing
different. Then read the C1 annotation. The annotation text pattern:

```
"Of the GBP 4,120 this use case is told it costs here,
 GBP 1,860 (45 percent) is allocated by rule, not observed."
```

Do NOT show a ranked estate table by default. It exists behind a
"Rank nodes by rule share" button so the practitioner can find it and
the executive is not confronted with it.

Do NOT show any figure labelled "true cost". There is none.

### 4.3 View 3: Risk

Purpose: show propagation and non-additivity.

Tap a platform, press "Fail it". Animation: the node pulses, then
edges light in sequence outward with delay proportional to hop count,
each edge lighting with probability equal to its
conditional_failure_prob (sampled per run, so pressing again gives a
different pattern). Affected use cases turn to a distinct shape state
(wireframe) and their subdomain hulls flash once.

Blast radius readout: number of use cases affected, number of
subdomains crossed, monthly business volume interrupted.

Panel: a loss exceedance curve for the selected node or for a selected
set of use cases, computed by Monte Carlo in the worker (10,000 runs
default, 100,000 on request). X axis GBP loss, log scale. Y axis
probability of exceeding. A movable budget line (default GBP 500k) with
a readout of exceedance probability at the line.

The non-additivity exhibit, mandatory:

```
Select a subdomain. The panel shows two P99 figures:
  "Sum of per-use-case P99 losses"        GBP X
  "P99 of the subdomain's joint loss"     GBP Y
with the sentence: "These differ because the use cases share
platforms. Adding them counts the same failure many times."
```

Dependence control: a slider from independent to comonotonic, with
the joint P99 updating live. Label the endpoints in plain English:
"platforms fail on their own" to "platforms fail together". Show the
band width in GBP.

### 4.4 View 4: Footprint

Purpose: show accretion and silent exit cost.

A time scrubber, month 0 to month 60. Select a platform, default the
cloud data platform. As the scrubber advances, use cases attach to it
in the order of their adopted_month. Three readouts, all per platform,
all in GBP per month or GBP:

```
Metered spend         rises with attached volume
Rule share            the fixed pool, spread over more riders,
                      so per-rider share FALLS while the total
                      arbitrary GBP on the estate's figures rises
Exit cost             execution + option, rises with tenure and
                      fan-in. This is the line nobody is shown.
```

A vertical marker labelled "Ratified as strategic" at a configurable
month (default 31). The panel text at that marker:

```
"By the time this platform reached the board, 17 use cases in
 5 subdomains already depended on it and exiting would have
 cost roughly GBP 2.4m. The board ratified a footprint."
```

The number in that sentence is computed, not hard-coded.

Optional overlay: a FinOps-style spend chart on the same time axis,
showing that the metered spend was visible throughout and the exit
cost never was. Two lines, one labelled "what the bill showed", one
labelled "what it committed you to".

### 4.5 View 5: Two shapes

Purpose: concentration versus best of breed, honestly.

Split screen, two graphs, same use cases.

```
LEFT   Concentrated. Four platforms carry most of the estate.
       Integration layer thin.
RIGHT  Best of breed. Twelve platforms, each carrying few
       use cases. Integration layer thick: the iPaaS, gateway
       and bus nodes have HIGH fan-in.
```

Shared readouts, side by side, per subdomain (never totalled):

```
Per-unit metered cost          left cheaper, usually
Rule share proportion          left higher per node, right
                               spread across more nodes
Joint P99 loss at budget line  left fatter tail
Largest single blast radius    left: a platform. right: the
                               integration node. Highlight this.
Exit cost, largest single      left: huge, one node. right:
                               smaller per node, but sum of
                               integration commitments shown
                               alongside with the caveat that
                               it does not add cleanly.
```

The one sentence this view must land, shown when the user toggles
between the two:

```
"Diversifying platforms did not remove the concentration. It
 moved it to the integration layer. The graph shows where it
 went. The org chart does not."
```

### 4.6 View 6: Boundaries

Purpose: show that boundaries are declared, and what depends on them.

Let the user drag use cases from one subdomain hull to another, or
merge two subdomains, or split one. Then show what changed and what
did not:

```
CHANGED       which use cases share which pool under "by
              headcount" or "by volume" rules
UNCHANGED     the rule share under equal split, because R23
              makes the fixed basis partition-independent
UNCHANGED     the graph. Edges do not move. Risk does not move.
CHANGED       which edges now cross a boundary, and therefore
              whose decision becomes whose dependency
```

Render boundary-crossing edges distinctly (dashed). Count them.

Text at the top of the panel, always visible in this view:

```
"The graph is mined. The boundaries are drawn by people.
 Redraw them and watch which numbers move. The ones that
 move are the ones you should trust least."
```

Do NOT imply that some boundary placement is correct. There is no
correct placement in this tool. Do NOT show cost "accumulating" at
boundaries. That claim was retired.

## 5. THE DETAIL PANEL

Opens on tap. Same panel component for all node types with sections
shown or hidden by type.

### 5.1 Platform

```
Name, category, type
Fixed pool GBP/month, driver name, unit cost
Riders: count of use cases, count of subdomains
Metered spend GBP/month (sum of edge spend, this one DOES add
  because it is one meter)
Rule share: fixed pool divided per current rule
C1: proportion of riders' reported cost that is rule
Failure: LEF per year, loss distribution summary (median, P90)
Blast radius: use cases, subdomains, volume at risk
Exit cost: execution GBP, option GBP, with one-line explanation
  of each (see 5.4)
Adopted: month
```

### 5.2 Use case

```
Name, subdomain, volume per month
Cost per volume unit, GBP, as a RANGE: metered part exact,
  rule part with the current rule and with the two alternatives,
  so the range is the spread across rules. This is the honest
  number.
Platforms depended on, with edge spend each
Risk: probability of interruption per year, expected volume
  interrupted, loss exceedance mini-curve
Exit: which platform exits would strand this use case
```

### 5.3 Integration node

Same as platform, plus a highlighted line:

```
"This node exists because the estate is diversified. Its
 fan-in is the concentration that diversification created."
```

### 5.4 Switching cost, how to explain it on screen

Two components, always shown separately, never summed into one
"lock-in" figure without both parts visible.

```
Execution      what it costs to actually move: migration effort,
               dual running, retraining. Estimated in GBP.
Option         what you gave up by committing: the value of
               being able to choose differently, which fell as
               tenure and fan-in rose. Estimated in GBP.
```

Plain-English tooltip for the option component:

```
"When you first adopted this, you could still have picked
 something else cheaply. Every use case you attached made
 that harder. This number is the price of the choices you
 no longer have."
```

Do NOT present the option component as something added to cost. It is
a decomposition of switching cost. If the UI ever shows
"cost + option" as a single figure, that is a bug.

## 6. FORMULAS (illustrative, synthetic)

All GBP. All per month unless stated. Keep these in one file,
/src/model/ledger.ts, with comments matching the labels here.

```
edge_spend(uc, p)        = volume(uc) * units_per_volume(uc,p)
                           * unit_cost(p)
metered_spend(p)         = sum over riders of edge_spend
rule_share(p, uc)        equal:     fixed_pool(p) / n_riders(p)
                         by_volume: fixed_pool(p) * volume(uc)
                                    / sum volume(riders)
                         by_head:   fixed_pool(p) * size(sub(uc))
                                    / sum size(subs of riders)
reported_cost(uc, p)     = edge_spend(uc,p) + rule_share(p,uc)
C1(p)                    = sum rule_share(p, riders)
                           / sum reported_cost(riders, p)
                         = fixed_pool(p) / (fixed_pool(p)
                           + metered_spend(p))
cost_per_unit(uc)        = sum over p of reported_cost(uc,p)
                           / volume(uc), shown as a range
                           across the three rules

risk, per Monte Carlo run:
  for each platform p: fails ~ Bernoulli(1 - exp(-LEF(p)/12))
    loss(p) ~ LogNormal(mu(p), sigma(p)) if fails else 0
  dependence: draw platform failures via a Gaussian copula with
    a single correlation parameter rho in [0, 1] from the
    slider; rho = 0 independent, rho = 1 comonotonic
  for each use case uc: interrupted if any platform p on its
    edges fails AND Uniform() < conditional_failure_prob(uc,p)
    loss(uc) = interrupted ? volume(uc) * margin_per_unit(sub)
               * outage_fraction : 0
  subdomain joint loss = sum over its use cases of loss(uc)
    (this sums WITHIN a run, which is legitimate; the exhibit
    compares the P99 of this joint quantity against the sum
    of per-use-case P99s, which is the illegitimate sum)

exit cost:
  exit_execution(p)      = base_exec(p) * (1 + 0.15 * n_riders(p))
  exit_option(p)         = base_option(p) * tenure_factor(p)
                           * fanin_factor(p)
    tenure_factor        = 1 + 0.02 * months_since_adopted
    fanin_factor         = 1 + 0.08 * n_subdomains(riders)
```

These coefficients are made up. Say so in a comment. They exist to
make the picture move in the right direction, not to be right.
